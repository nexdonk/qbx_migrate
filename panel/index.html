Start here

Everything you'd normally type into the server console or PowerShell, as buttons. Each step is a dry run first: it writes a report and changes nothing. Writing anything takes a second click and typing apply.

Use a copy. Run this against a copy of your server and a copy of your database first, never the live one. Take a full mysqldump before you start; the kit's own backups are precise but a full dump survives anything.

Connect the panel to your server

  1. Put qbx_migrate in your resources and add ensure qbx_migrate to server.cfg after oxmysql and ox_lib.
  2. Start the server. On first start it writes panel_token.txt into the resource folder; this panel reads it from there automatically.
  3. The pill in the top right turns green. If your server isn't on 127.0.0.1:30120, change it in Settings.

The order

  1. Code audit — scans your resources folder. Read-only. Doesn't need the server running.
  2. Database check — tells you whether you're on the QBCore or the ESX path.
  3. Migrate — QBCore or ESX, step by step, or everything at once.
  4. Swap resources — remove qb-core / es_extended, install qbx_core and the ox stack (the audit report lists exactly which).
  5. First logins — leave qbx_migrate ensured; players' identifiers are fixed as they join.

Settings

Saved next to the panel in panel/settings.json.

Server on another machine? Copy the token out of resources/…/qbx_migrate/panel_token.txt on the server into the field above, and add set qbx_migrate_panel_remote true to its server.cfg. By default the server only answers this panel from the same machine.

Code audit

Scans every .lua, fxmanifest and .cfg in your resources folder for QBCore / ESX code that needs changing. Runs on this machine; the server doesn't need to be on.

Audit read-only

Writes MIGRATION_REPORT.md and findings.csv. The HIGH section is your actual workload.

Apply safe rewrites writes files

QBCore servers only. Mechanical mappings only (exports['qb-core'] ➜ qbx_core, qb-target ➜ ox_target compat, string job grades, manifest dependencies). Every touched file is backed up and a restore script is generated.

Database check

Read-only looks at your database, run through the server. Check tells you which path you're on.

QBCore ➜ Qbox

Run top to bottom. Dry run each, read the report, then apply.

ESX ➜ Qbox

The ESX step renames users ➜ esx_users (never drops it), creates the qbx tables and only ever adds rows. It's idempotent: re-running keeps every character's citizenid and refreshes the data.

Then merge the generated files, swap resources, restart with qbx_core + ox_inventory, and dry run Convert ESX database again: “Items NOT defined in ox_inventory” must be empty. If it isn't, add the items and apply again.
Undo everything this step did: Restore & rollback ➜ ESX rollback.

Run everything

Every applicable step in order, one report. The ESX step is included automatically when an ESX users table is detected.

First logins

Qbox keys players by license2:, which can't be computed offline. qbx_migrate rewrites each player's rows as they connect. Keep it ensured until nothing is pending.

Restore & rollback

Restores put data back, not schema: added columns and tables stay (they're harmless). A true point-in-time reset is what your own mysqldump is for.
